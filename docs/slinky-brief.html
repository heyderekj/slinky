Why

Keys under the doormat

Building solo with AI tools means juggling dozens of keys across a dozen repos. Right now they're kept in the least safe places on your Mac.

~/harvous/.env

.env files are open books

Every repo has one. Claude Code, Cursor and Codex read them straight into their context, and the transcripts keep them.

~/Downloads/github-recovery-codes.txt

Recovery codes live in Downloads

Right next to last week's invoices. Binky can sort them. Nobody should have to.

Passwords › Notes field

Passwords is for logins

Apple Passwords wants a website and a username. API keys, webhook secrets and backup codes end up in a notes field.

How it works

Values go down, names go up

Only Slinky.app ever decrypts anything. The CLI and the MCP server are thin clients. Real values go down into the process that needs them; only names and masked output go back up to the model.

One encrypted fileKeys, projects and codes live in an encrypted vault in Application Support. Time Machine-safe as is.
Its key is locked twiceOnce to this Mac's Secure Enclave (Touch ID or password), once to a printed Recovery Key for backups and new Macs.
One unlock per sessionIdle lock after 10 minutes, hard lock after 12 hours, and on sleep, screen lock or "Revoke Agent Access".
Every caller is checkedThe socket confirms it's Slinky's own CLI, then walks the process tree so the card can say "Claude Code › zsh › npm".

Two signing tiers, one design

Slinky can ship before a paid Apple Developer account. Getting one later is an upgrade, not a rewrite.

Agents

A CLI and an MCP server that never hand over values

Agents run commands through slinky run in their own shell, so their own sandbox and permission prompts still apply. The MCP server only lists, checks and asks.

# run anything with the project's keys; known values are masked in the output
slinky run -- npm run dev
slinky check                     # what .env.example needs vs. what Slinky has
slinky ls --json                 # names and metadata, never values
slinky request RESEND_API_KEY    # opens the "paste it here" sheet and waits
slinky import .env --trash       # tuck a file away, then move it to the Trash
slinky connect claude            # also: cursor, codex, claude-desktop
slinky mcp                       # the MCP server, over stdio

MCP tools

  • list_projects, list_secrets: names, kinds, test or live
  • check_env: what's missing for this folder
  • request_secret: you paste in Slinky; it returns "added" or "declined"
  • describe_policy: which commands are already approved

Never exposed

  • Values, reveal, clipboard or export
  • Writing .env files, or set_secret(value)
  • Delete, rotate, or changing approvals
  • Recovery codes, or anything derived from a value

When an agent is the one asking

  • Touch ID for each command, showing the exact command, the folder and the process chain.
  • Shell one-liners like sh -c, node -e, curl, printenv and git push are refused by default.
  • Live keys are human-only unless you flip them. Agents get the test key.
  • Every release is logged in Activity and gets a notification with no secret details in it.
  • Connect sets up Claude Code, Cursor, Codex and Claude Desktop in one click: it shows a diff, keeps a backup, and blocks agents from reading .env files.

The AI era

Local root, cloud reach

More agents run in the cloud now: Claude Code on the web, Codex cloud, Cursor cloud agents, Copilot's coding agent, app builders like Lovable and Convex Chef. Slinky doesn't follow them there. It stays the one place the real keys live, hands the cloud scoped copies, and remembers where every copy went.

About Convex and sandboxes

When Convex says "sandbox" it mostly means Components: "sandboxed building blocks" an agent can't reach across. For cloud agents that can't log in, its Agent Mode mints a deploy key scoped to one dev deployment. That's the cleanest "give the agent its own narrower key" model out there, which makes Convex the natural first provider for Slinky to mint keys for. Convex hasn't said anything about agent-safe secrets beyond that, so there's room.

What the cloud era adds to the roadmap

  1. Exposure ledger and rotation assist v1Every copy, push and injection is logged. When a session ends, Slinky asks what to rotate and opens the right page.
  2. Exact-value leak scanner v1Slinky knows the real values, so it finds them in exported transcripts, CI logs and git history with no false alarms. Matching happens in memory only.
  3. Names-only env manifest v1A committed list of what a project needs (name, provider, scopes, allowed hosts). Cloud agents read it and know what to ask for. Aligned with Varlock's .env.schema rather than a new format.
  4. Proxy configs for local agents v1Writes Claude Code's sandbox.credentials mask entries, so commands see a stand-in and the real key only goes to the right host.
  5. Mint instead of share v1.xConvex first, then Cloudflare, OpenAI project keys, AWS STS and GitHub App tokens. Touch ID on every mint, since that's when the admin key comes out.
  6. Push with provenance v1.xVercel, Netlify, Convex, GitHub Actions and Codespaces through their APIs. Claude Code cloud, Codex and Cursor have no API yet, so those get copy once and "mark as placed".
  7. Approve from iPhone or Watch laterNeeds a relay, and Bitwarden and 1Password are already building one. Worth checking whether Slinky can plug into Bitwarden's open Agent Access protocol instead.

Personal and commercial

Five people who need this

Most new builders aren't developers. Lovable reports about 8 million users. GitGuardian counted 1.27 million leaked AI-service keys last year, up 81%. One solo developer got an $82K Gemini bill in 48 hours from a stolen key.

The weekend builder

Can't tell a publishable key from a secret one. Pastes keys into the chat.

Labels like "safe in a browser" and "server only", a "what is this key?" check on paste, and a one-screen "I leaked a key" guide for each provider.

The tinkerer

Tokens in .mcp.json, dotfiles and cron scripts.

slinky run, a helper that swaps hardcoded MCP tokens for references, and a scan of existing configs.

The freelancer

Client keys in Notion, Slack and email. No clean handoff when a project ends.

One workspace per client, a handoff package with a rotation checklist, and "Forget this client".

The solo SaaS founder

Live vs. test mix-ups, rotation, and the first security questionnaire.

Touch ID on live keys, key-age reminders, "where is this key used", and an exportable access log.

The two-person team

Needs to share one key without another SaaS seat.

Share with one person, with an expiry, then a nudge to rotate when access ends.

One paste, the right drawer

On one day this October, Derek had a recovery key, a personal API token and an env secret, each with a page telling him to "store it somewhere safe". Tuck It Away (one shortcut, a tiny window) takes each paste and suggests where it goes: the recovery key to Kept with a nudge to print a copy, the token to Keys with an optional expiry, the env secret to a project so slinky run can use it. That's the test the first version has to pass.

What Slinky won't be

  • A hosted vault, a sync service or a team secrets platform (Doppler, Infisical, 1Password)
  • A cloud proxy or sandbox host. Vercel, Cloudflare, Daytona, Modal and Anthropic already run those; Slinky feeds them.
  • An OAuth broker (Arcade, Composio) or an enterprise agent-identity product (Keycard, Aembit)
  • A pattern-matching scanner competing with GitGuardian. Its edge is exact values.
  • Anything that hands a value to a model, "just this once" included

Honest limits

What Slinky can't promise

These go on the site word for word. Saying them plainly is part of the trust story.

  • An approved command gets the key. A tricked agent can still try to leak it through a script you approved.
  • Once a value is in a process's environment, other programs running as you can read it.
  • Masking catches known values. Encoded or split-up values can slip past it.
  • Root, and apps with Accessibility permission, can get around the prompts.
Slinky keeps secrets out of the model and off your disk. It isn't a sandbox.
